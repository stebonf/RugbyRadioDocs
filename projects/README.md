# Projects

`projects` contains initiative-specific working material.

A project is a bounded initiative: a feature, migration, refactor, research effort, product analysis, SEO effort, architecture change, implementation slice, or any other body of work that deserves its own context and artifacts.

Projects are working spaces. They are not the wiki and they are not the reusable company kit.

## Core Idea

Use `projects/<project-id>` to keep all temporary and evolving material for one initiative together:

- analysis;
- architecture;
- task planning;
- decisions;
- research;
- notes;
- raw working inputs;
- taskboards and status.

When the initiative is finished, create a final closeout document under `raw/projects/<project-id>`. That closeout document becomes structured source material for future wiki ingestion.

## Project Id

Use lowercase hyphen-case:

```text
projects/nextjs-migration
projects/seo-audit
projects/user-profile-redesign
```

The project id should be:

- short;
- stable;
- descriptive;
- independent from temporary branch names or ticket numbers unless those are the real initiative identifier.

## Standard Structure

Recommended structure:

```text
projects/
  <project-id>/
    README.md
    analysis/
    architecture/
    tasks/
    decisions/
    research/
    raw/
    notes/
```

Use only the folders needed by the project. Do not create empty structure for its own sake unless an agent or skill expects it.

## Folder Responsibilities

`README.md`

Project overview, status, scope, links to key artifacts, and closeout reference.

`analysis/`

Functional analysis, product analysis, SEO analysis, audits, discovery notes, and structured problem analysis.

`architecture/`

Technical design, architecture decisions, system impact, API/data/component plans, sequencing, and risk analysis.

`tasks/`

Task lists, taskboards, implementation plans, validation plans, and execution tracking.

Each Markdown file under `tasks/` is also treated by the company dashboard as a runnable project task. Prefer one focused task per file when the task should be assigned to an agent from the dashboard.

Recommended task metadata:

```markdown
---
id: task-short-id
title: Human readable task title
status: open
agent: agent-name
priority: medium
---
```

Task status values:

- `open`: default, not completed;
- `ready`: clarified and ready to run;
- `running`: execution is active;
- `blocked`: waiting for answers, access, or decisions;
- `done`: completed and hidden by the dashboard default open-task filter.

`agent` is optional. When present, the dashboard preselects that agent in the project task tab. The user can still override it manually before queuing the task.

Tasks can be created manually or generated by `agent:task-planner` from an editable workflow under `company/workflows`.

`decisions/`

Decision records that matter during the initiative: selected option, rationale, alternatives, trade-offs, and date.

`research/`

External research, competitor notes, experiments, benchmarks, references, and investigation outputs.

`raw/`

Project-local raw inputs used during the work. These are not final wiki raw sources. Final closeout raw sources belong in top-level `raw/projects/<project-id>`.

`notes/`

Scratch notes, meeting notes, working observations, and temporary context that may or may not become formal artifacts.

## Project README

Each substantial project should have:

```text
projects/<project-id>/README.md
```

Recommended content:

```markdown
# <Project Name>

## Status

## Goal

## Scope

## Out Of Scope

## Key Artifacts

## Current Decisions

## Open Questions

## Task Status

## Closeout
```

## Status Values

Use simple status values:

- `idea`: not yet analyzed;
- `analysis`: functional/product/SEO analysis in progress;
- `architecture`: technical design in progress;
- `planned`: tasks exist but implementation has not started;
- `in-progress`: implementation or execution is active;
- `blocked`: waiting for decision, access, dependency, or missing input;
- `done`: work is complete;
- `closed`: closeout document exists in `raw/projects/<project-id>`.

## How LLMs Should Use Projects

Before working on an initiative:

1. Identify the relevant `project-id`.
2. Read `projects/<project-id>/README.md` if it exists.
3. Read only the relevant files under `analysis`, `architecture`, `tasks`, `decisions`, `research`, `raw`, or `notes`.
4. Prefer project artifacts over broad repository search when the task is clearly within that project.
5. Keep new initiative artifacts inside the same project folder.

When executing a project task from the dashboard, treat the selected task file as the immediate scope. Read the task, the project README, and only the supporting artifacts needed to complete that specific task. If the task is ambiguous, ask questions instead of broadening the work silently.

If no project exists and the user asks for initiative-level work, create one when the scope is clear. If the scope is not clear, use `projects/_inbox` or ask for a project id.

## Relationship With Company

`company` contains reusable operating rules: skills, prompts, and agents.

`projects` contains project-specific work.

Do not put reusable company process inside a project. If a project produces a repeatable method, generalize it and move it to `company`.

## Relationship With Raw

`projects/<project-id>` is the working area.

`raw/projects/<project-id>` is the final source-material area.

At project completion, use the `finalize-project` skill to create:

```text
raw/projects/<project-id>/<project-id>-closeout.md
```

The closeout should summarize:

- original goal;
- final outcome;
- completed scope;
- incomplete or deferred scope;
- functional changes;
- architectural changes;
- implementation summary;
- decisions;
- changed files or components;
- validation;
- known gaps;
- follow-ups;
- source documents;
- wiki ingestion notes.

## Relationship With Wiki

The wiki contains consolidated knowledge.

Project files should not directly replace wiki pages. Instead, a completed project produces a closeout document in `raw/projects`, and that raw document can later feed wiki updates.

Do not edit the wiki from a project workflow unless the user explicitly asks for wiki ingestion or wiki maintenance.

## File Naming

Use lowercase hyphen-case for generated artifacts:

```text
functional-user-profile.md
arch-user-profile.md
tasklist-user-profile.md
taskboard-user-profile.md
decision-auth-session.md
seo-public-pages.md
```

Do not overwrite existing artifacts. Add `-02`, `-03`, or a more specific suffix.

## Working Rules

- Keep project artifacts focused on the initiative.
- Keep assumptions and open questions explicit.
- Separate working notes from final closeout material.
- Prefer repository-relative paths.
- Do not store secrets, credentials, tokens, private keys, or unfiltered sensitive exports.
- Preserve useful context, but avoid dumping every intermediate note into formal artifacts.
- When closing a project, make the closeout self-contained enough for future wiki ingestion.

## Minimal Project

For small initiatives, this is enough:

```text
projects/<project-id>/
  README.md
  tasks/
```

For analysis-first initiatives, this is usually enough:

```text
projects/<project-id>/
  README.md
  analysis/
  architecture/
  tasks/
```

For completed initiatives, ensure this exists:

```text
raw/projects/<project-id>/<project-id>-closeout.md
```
